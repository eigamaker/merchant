## 1. この文書の位置づけ

ロードマップの段階1（事実と知識の分離）はコードに入った。[playerKnowledge.ts](../src/game/playerKnowledge.ts) が報告を配信待ちで抱え、地下にいるあいだ町の報せを渡さず、序列表は `knowsNpcDeath` を読む。本書は**その先**、段階2〜4にあたる範囲の提案をまとめる。

各案に `S-2` 以降のIDを振り、票は [DESIGN_BACKLOG.md](DESIGN_BACKLOG.md) に置く。ここで使う型名・欄名は仮称であり、存在するフィールドではない。数値は例で、確定値ではない。「現状」は2026-09-12時点の作業ツリーをコードで確認した挙動を指す。

評価はコアストーリーの6点で行う。商人らしさ、商いと攻略の接続、知りうる形で届く結果、選択の葛藤、不在中も動く世界、小規模開発で実現できる範囲。

## 3. 提案

### S-2 売った品を、実際に使わせる

**現状** —— 装備が探索に効くのは `npc.gear`（商人が預けた印）に入った品だけである。店で買われた武器は `inventoryIds` に積まれるが、`npcCombatStats` も `gearPower` もそれを読まない。回復薬も同様で、画面内で行き合った冒険者が使う経路は [engine.ts](../src/game/engine.ts) にあるが、画面外の町処理では使われない。

**提案** —— 「所持」と「使用」を分ける。`gear` は預かりの契約なので潰さず、実際に身に着けているものを別に持つ。

```text
npc.equipped { weaponId?, armorId? }   ← 本人が選んで身に着けているもの
npc.gear     { weapon?, armor? }       ← 商人が託した印（S-3 で簡素化）
```

- 朝の町処理で、冒険者は `inventoryIds` から自分にとって最良の武器・防具を選んで装備する
- 薬は `recovering` の回復を早める、または `delve` の死亡判定を一度だけ肩代わりして1チャージ消費する
- 食料は遠征の日数上限になる（S-7 の物資と同じ欄を使う）

**既存のどこに乗るか** —— `finishDelve` が渡している `gearPower` を、装備込みの値へ広げるだけで足りる。効き幅の上限（現行 `Math.min(0.10, …)`）は据え置く。良い装備で深層が作業になってはいけない。

**物語上の意味** —— 帰還報告に「あなたが売った革鎧が効いた」「薬が一本足りなかった」が乗る。ロードマップ§8-7の受け入れ条件（**持っているだけの品を装備扱いしない**）をそのまま満たす。売買が世界の出来事につながる最初の一本で、S-4・S-9 はこの上に乗る。

**規模と注意** —— 小。遠征（S-7）を待たず、いまの1日潜行のままで因果が閉じる。誰が何を装備しているかは世界の事実であり、商人が知るのは帰還報告と、迷宮で行き合ったときだけである。掲示に装備欄を出さない。

### S-3 貸与を廃止し、「託す」一本にする

**現状** —— `NpcGearTerm` が `"lent" | "given"` の二択で、次の差がある。

| | 信頼 | 関係 | 返却 | お抱えの道 |
|---|---:|---:|---|---|
| 貸与 | +4 | ― | 町で会った翌日に自動で返る。2〜35%で返さない（`withholdsLentGear`） | 未返却が付くと閉じる |
| 譲渡 | +15 | +5 | 返らない | 開く（`retainerReady` が `term === "given"` を要求） |

これを支えるために、`term` と `withheld` の2欄、`withholdsLentGear` と `settleLentGear`、町の日次ループの1経路、[npcGear.test.ts](../src/game/npcGear.test.ts) の17件中6件ほどが存在している。

**そのうえで、実際には次の二つが起きている。**

1. **町の冒険者へ貸した装備は、画面外の探索で一度も担がれない。** `settleLentGear` は `simulateTownDay` の同じループ内で、出発判断より前に走る。貸した翌朝にはもう返っている。貸与が装備支援として効くのは、日次ループから除外される護衛（`contracted` / `escorting`）に対してだけで、それは実質「その探索のあいだ持たせる」でしかない。
2. **「譲った品は返らない」という約束を守っているのはUIだけである。** `reclaimGear` は `term` を見ない。[MerchantScene.ts](../src/scenes/MerchantScene.ts) の `openNpcGear` が選択肢を `disabled` にしているだけで、ルールがロジック側に無い。

**提案** —— `NpcGearTerm` を廃止し、預けるという行為を**「託す」一つ**にする。失われる体験は場面を移して残す。

| 廃止するもの | 移し先 |
|---|---|
| `NpcGearTerm`、`entrustGear` の term 分岐 | 託した品の価値で信頼の伸びを決める（現行 `given` の +15 を基準にする） |
| `withholdsLentGear`、`settleLentGear`、日次の自動返却 | **返却は商人が申し出たときだけ起きる。** `reclaimGear` が相手の性格・信頼・その品の功績から、素直に返す／渋る／断るを返す |
| `NpcGearSlot.withheld` の付き方 | 断られた事実として残し、お抱えの道を閉じる役割はそのまま引き継ぐ |
| `retainerReady` の `term === "given"` 条件 | **託したまま、引き取らずに生還を重ねたこと**を条件にする |

**物語上の意味** —— 商人の選択は本来「貸すか譲るか」ではなく、**この品を手放して、死ぬかもしれない誰かに持たせるか**である。契約の種類はその問いを薄めるだけで、どちらでも品は担がれ、来歴を負い、持ち主と共に失われうる。

返却の駆け引きは消さずに、背景のサイコロから**商人が手を伸ばす場面**へ移す。「それ、もう俺の得物なんですがね」と言われる瞬間のほうが、翌朝の自動返却より強い。しかもそれは §7 の「品はいつ誰のものになるのか」そのもので、S-4（遺品の帰属）と同じ問いの、生きている相手版になる。

お抱えの条件を「渡し切った」から「**返せと言わなかった**」へ移すのも、関係の作り方として素直である。

**規模と注意** —— 小（削除が主）。日次ループから1経路、セーブから1欄、テストから6件ほどが減る。そして所有の曖昧さが一つ減る —— ロードマップ§4.4が「`owner` や `location` だけから法的な所有を判定しない」と警告している当のものが `term` なので、**所有と来歴（S-5）と遺品の帰属（S-4）に手を付ける前に片付けておきたい。**

失うものも書いておく。「高価な品を試しに持たせる」低コミットな入口は無くなるが、託したうえで引き取りを申し出られるので実質は残る。ただし相手が渋る可能性がある以上、以前より重い判断にはなる。それは意図した重さである。

既存セーブは `lent` / `given` のどちらも「託した」に畳む。`withheld` は保持する。

### S-4 遺品の帰属（遺族・仲間・回収者）

**現状** —— 遺体から回収した品は、その場で商品になる。縁のある相手が死ぬと訃報は届き、`historyV2` に `ownerDied` が残り、遺銘まで刻まれるが、**誰もそれを取り返しに来ない。**

**提案** —— 縁のある冒険者が死に、その遺品を商人が回収したとき、訃報の数日後に遺族か仲間が店を訪ねる。「あの人の◯◯を返してほしい」。

選択は**返す／売る／黙って持っている**の三つで、どれも採点しない。返却は金にならず、言葉と縁だけが残る。売った場合、相手がそれを知るかどうかは情報の経路（S-8）に従う。

**既存のどこに乗るか** —— 既存の `TimedEvent` と `effect: { kind: "arrival" }`、[npcRoster.ts](../src/game/npcRoster.ts) の `createTownsperson`、`dungeonCorpses` の遺品ID、`npcBonds` にほぼ追加なしで乗る。`announceSingularFind` が蒐集家を呼ぶのと同じ形である。

**物語上の意味** —— **プロローグを待たずに「物はいつ商品になるのか」が遊べる。** 幼少期の剣の選択（§4）は、後からこの仕組みの最初の一回として差し込める。「回収者のものになる」という慣習を町の既定にするかどうかも、ここで一度決めておける。

**規模と注意** —— 小。物語の核心に対する費用対効果が最も高い。遺族NPCを名簿に足すので、剪定で消えない条件（S-5）を先に決めておく。

### S-5 重要品の保護と、通常品の要約

**現状** —— 保持されるのは手元・遺体・預けた装備・台本15人の非迷宮品で、重要さの軸が無い。判定はレアリティと `singular` と `deeds` の有無に寄っている。遺体は5日（形見つきで14日）・12件上限、`archive` は売却済みを全件抱えたまま伸び、[merchantEconomy.test.ts](../src/game/merchantEconomy.test.ts) に60,000字の上限がある。

**提案** —— `ItemInstance.narrativeRole?: "keepsake" | "worldImpact"` を、レアリティと独立に置く。

- `narrativeRole` を持つ品は、剪定・遺体台帳・`archive` の整理すべてで無条件に残す
- 代わりに**通常の売却済み品は1行の要約へ畳む**。誰に、いつ、いくらで売ったかだけを残す
- 追跡することと、手元から失われないことは別である。売却・返却・紛失・廃棄は成立し、その結果が記録される

**物語上の意味** —— 幼なじみの剣を、150Gの `iron-sword` のまま、普通の安い剣として保持できる。§4の「物語上の重要性とレアリティは別」をデータで表す唯一の欄になる。

**規模と注意** —— 小。段階3の前提であり、段階4（売却後の結果）の追跡対象を絞る道具でもある。`archive` の要約は上限テストの対策も兼ねる。

### S-6 日次更新の窓口を一つに

**現状** —— [merchantSystems.ts](../src/game/merchantSystems.ts) の `advanceTime` と `restUntilMorning` が、それぞれ `resetDailySystems` → `simulateTownDay` → `processDayEvents` を呼んでいる。

**提案** —— `advanceWorldDay(state)` へ集約し、順序を固定する。

```text
日を跨ぐ → 期限の精算 → 遠征を1日進める → 町の一日 → 予定された出来事を世界へ反映 → 報告の配信
```

複数日を進める場合は一日ずつ順に処理する。日次処理済みの印と乱数の引き方（キャンペーンID・日付・人物ID）は現行のまま維持する。

**規模と注意** —— 小。**いまは結果を変えないリファクタとして単独で入れられる。** 遠征（S-7）と配信遅延（S-8）が入ってから順序を直すと、再現性の崩れをテストで捕まえにくくなる。先に置く。

### S-7 遠征（数日）と帰還遅延

**現状** —— `npc.delve` は `{ floor, departedDay }` だけを持ち、翌日の町処理で生還・負傷・死亡のいずれかに決着する。複数日、物資、撤退、帰還予定、未帰還が無い。

**提案** —— キャンペーン側に `Expedition` を置き、`npc.delve` から段階的に移す。最小形は**1人・一往復**でよい。

```text
Expedition {
  id, memberIds, departedDay,
  declaredFloor, plannedDays,        ← 出発時に町へ告げた計画
  supplies { provisions, medicine },  ← 商人が売った物資
  backing,                            ← 出資・装備支援の契約
  reachedFloor, settledDay            ← 世界の事実。公表は報告を経る
}
```

- **公表と実際を分ける。** 掲示が読むのは `declaredFloor` と `plannedDays` だけで、予定を過ぎて未確認なら「**帰還遅延**」。全滅を内部で知っていることを理由に「死亡確認」へ変えない（`knowsNpcDeath` にそのまま接続できる）
- **商人の関与点** —— 物資の販売が `plannedDays` を決め、装備支援が `declaredFloor` を押し上げ、出資が分け前の権利になる。**深い階を目標にさせるほど、戻る品は良く、戻らない確率が上がる。** 「自分の目的のために、他人をどこまで危険にさらせるか」が、初めて数値として現れる
- 護衛契約（商人が同行する）と、同行しない遠征への出資は別の契約として扱う

**先に決めるべき境界** —— `partyAndFloorNpcIds` は現在階と訪問済み `floorStates` のNPCを日次処理から外すが、遠征が複数日になると、**その場のターン処理と画面外の日次処理が同じ人物を二重に動かす**余地が広がる。二重死亡と品の複製の入口なので、型より先にこの責務境界を決める。

**規模と注意** —— 大。設計はここを先に詰める（ロードマップ§7のとおり）が、コードの投入は S-2・S-3・S-4 の後でよい。日数・成功率・出資額・物資量はここで固定しない。

### S-8 情報の経路と、遅れと誤り

**現状** —— `InformationReport.reach` は `"town" | "immediate"` のみで、誰が伝えたかを持たない。`availableDay` はあるが、`queueReport` の既定が発生日なので遅延が使われていない。誤報と訂正が無い。

**提案** —— 報告に情報源と確度を足す。

```text
InformationReport { …, source: "return" | "guild" | "tavern" | "peddler" | "evidence", confidence }
```

- 噂は `availableDay` を遅らせ、内容を欠落・誇張させる。**世界の事実は変えない**（虚偽の `WorldEvent` を作らない）
- 後から届いた確かな報告が同じ `subject` を上書きし、日誌には両方が残る。`journalLine` は既に発生日と取得日の差を表示できる
- 訃報は「予定超過 → 帰還遅延 → 捜索または遺体の発見 → 判明」の順を通る。差分2と4はここで解ける

**規模と注意** —— 中。`KnownDeath` に情報源と訂正の印を足す程度で済む。真偽の内部判定を、そのまま画面へ「真実」「嘘」と出さない。

### S-9 公表される到達記録と、町の発展

**現状** —— `DUNGEON_MAX_FLOOR = 30` だが誰も攻略へ向かわず、名簿目標は `ADVENTURER_ROSTER_TARGET = 30` の固定値で、増える理由が死者の補充しかない。町は発展しない。

**提案** —— 世界に二つの数を置く。`worldDeepest`（World Truth）と `publicRecord`（帰還報告で公表された最深到達）。**商人が支えた遠征だけが `publicRecord` を押し上げる。**

- 記録が上がると、名簿の目標人数とランク構成、来客数、棚の枠、買い手の予算が動く
- 同時に、仕入れ値・家賃・供給の逼迫も上がる。発展そのものを悪としないまま、負担が出る
- **C-1「店の格」を金で買う方式ではなく、町の成長の結果にする**ほうが §6 に合う

§5の「青い鉱石の転機」は、既存の大量発注（[bulkOrders.ts](../src/game/bulkOrders.ts)）が経路の半分を持っている。転売で生きる商人へ卸した素材が町の外で評価され、噂が戻って冒険者が来る、という形なら既存機構の再利用で組める。

**規模と注意** —— 中。攻略後の町（§6）は未確定のままでよい。この案が引き受けるのは「**近づいていることが読める**」までである。迷宮を消すために冒険者を集め、集めるほど町が迷宮に依存していく、という矛盾がここで初めて数字になる。

### S-10 時間帯を「誰に会えるかの窓」に

**現状** —— `timeSlot` は開店可否と食料と露店にしか効いていない。

**提案** —— B-5 の「時間帯を資源ではなく、誰に会えるかの窓にする」案を、遠征の後に再検討する。朝の出発を見送る、夕方の帰還に居合わせる、夜に噂を聞く —— 遠征が入って初めて、時間帯に会う相手が生まれる。§8「日中の扱いは未確定」への最小の答えとして置く。

**規模と注意** —— 中。遠征（S-7）と情報経路（S-8）が入るまで着手しない。

## 4. 投入順

設計は遠征（S-7）を先に詰める。**コードの投入順はそれとは別で**、次を提案する。

| 順 | 案 | 理由 |
|---:|---|---|
| 1 | S-6 日次更新の窓口 | 結果を変えない土台。後から直すと再現性の崩れを捕まえにくい |
| 2 | S-3 貸与の廃止 | 削除が主。所有の曖昧さを、所有の設計に入る前に減らす |

| 4 | S-4 遺品の帰属 | 小さく、物語の核心に最も近い |
| 5 | S-5 重要品の保護 | S-4 で足すNPCと品を、剪定から守る |
| 6 | S-7 遠征 | 本命。S-2 が入っていれば支援の手応えが即座に出る |
| 7 | S-8 情報の経路 | 遠征の報告経路として意味を持つ |
| 8 | S-9 公表記録と町 | 遠征が公表記録を押し上げて初めて成立する |
| 9 | S-10 時間帯 | 会う相手が生まれてから |

## 5. 保存と移行

- 現在の `GameState.version` は15。S-2 / S-3 / S-5 でセーブの欄が増減するので、**この3件をまとめて version 16 の移行1回で通す**
- S-3 の `term` は読み捨て、`lent` / `given` のどちらも「託した」に畳む。`withheld` は保持する
- 新しい物語記録には `narrativeProgress` など別名を用いる。[save.ts](../src/game/save.ts) の `stripRetiredFields` が `story` / `quests` を無条件で削除する処理は外さない
- 未配信の報告、遠征の途中状態、重要品と故人への参照を、日次処理済みの印と一緒に保存する。ロードで発生済みの結果を再発火させない
- `pruneCampaignRecords` / `pruneCorpses` の保持対象に、未解決の遠征、未配信報告、`narrativeRole` を持つ品、S-4 の請求者を加える
