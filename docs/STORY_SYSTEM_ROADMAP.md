## 1. 今回の範囲と読み方

添付の設計更新をリポジトリの継続的な設計基準へ取り込み、2026-09-11時点の作業ツリーのコードと比較した。今回は設計資料を整備する。プロローグのプレイ実装、セーブ形式の変更、町・遠征の大規模改修は含めない。

以下の「現在」はコードで確認した挙動、「提案」は追加改善の案、「未確定」は設計判断が必要な事項を示す。作業ツリーにはこの資料整備より前から実装・アセットの変更があるため、この表は特定コミットの保証ではなく確認時点のスナップショットである。

## 3. 過去の判断との調整

原文の新案と、過去に採用・見送りとなった案を混同しない。履歴は台帳に残し、以下の整理を優先する。

| 旧判断 | 今回の整理 |
|---|---|
| 初期原文: 主人公が何かに触れて発生させた可能性、友の生死は不明 | 更新版で解消。発生原因ではない主人公と、死が確認された友を基準とする |
| A-1: 鑑定は作らず、来歴・証言で知る | 不確実性と知識獲得の代価は共通。専門鑑定機能を導入するかは再検討。原文の段階式鑑定をそのまま採用しない |
| B-1: 毎回1階から入り、その日のうちに帰る | 複数日の滞在は新しい方向に合わせて見直す。一方、深層から再出発できる拠点・楔・転移の採用は別件。野営の演出だけで深層再突入を解禁しない |
| B-5: 町の時間と迷宮の食料時計を独立させる案 | 世界時計を共通にする基準が優先。会える時間帯の窓は両立可能。40行動という現在値と最終時間設計も区別する |
| A-4 / D-1: 相場を動かすイベント、ギルドの報せ、一品物の所在一覧 | 発生と配信を分ける。所在は最終確認地点、実績は確認済み報告から表示する。単なるニュース文言の追加では成立しない |
| A-1 / D-1: 詳細来歴は銘・一品物に限定 | 普通の幼なじみの剣も重要記録になる。経済的な希少性とは別の追跡対象を提案する |
| C-2: 借金を作らない | 遠征出資の契約と、主人公の借金・冒険者への信用供与を分ける。初期原文の信用供与例だけで借金システムを復活させない |
| C-3: キャンペーンの終わりは保留 | 喪失の不可逆性、攻略後の町、未来を選ぶ方向を今回整理。エンディングの条件・分岐の実装は引き続き未確定 |
| B-4: 遠隔で救助を呼ぶ道具は作らない | ペットが実際に移動して助けを探す構想とは分ける。救助経路と探索失敗ルールの設計後に検討する |

## 4. 構成の提案

既存の `GameState`、人物ID、品UUID、日付を活かし、責務を順に分ける。以下の名前は実装前の仮称であり、存在するファイル・型ではない。

### 4.1 日次更新と情報の配信

```text
プレイヤーの行動・営業・休息
          ↓ 同じ時計
日境界を越える
          ↓
世界更新（遠征・到着・品・町など）
          ↓
実際の出来事を記録
          ↓
証言者・報告・証拠から情報の伝達を処理
          ↓ 主人公への到達条件を満たす
主人公の知識を更新 → 掲示・会話・履歴に表示
```

日次処理の窓口を `advanceWorldDay` などへ集約する提案とする。既存の朝処理、期限精算、NPC回復、町の更新の順序を明記し、移行の初段では現在の結果を保つ。複数日を進める場合は一日ずつ順番に処理する。日中の目撃・売買はその場で記録でき、情報配信も帰還や会話時に実行できるようにする。

**最初に `processDayEvents` の到着効果を配信処理から分離する。** 帰還まで報せを保留した結果、町への到着まで延期されてはいけない。`state.message` は表示用とし、世界の事実や唯一の保存先にしない。

同じ日・出来事を再実行しないIDと日次処理済み印を保存し、乱数は既存と同様にキャンペーン・日付・人物などから再現する。メニューを開く、報告を見る、ロードする操作では結果を抽選し直さない。

### 4.2 事実と知識のデータ

| 仮の責務 | 最小限の情報 | 利用側 |
|---|---|---|
| `WorldEvent` | 安定したID、発生日、種別、関係する人物・遠征・品ID、結果、原因となった出来事ID | 世界シミュレーション、結果の連鎖 |
| `InformationReport` | 報告ID、伝達者・証拠、作成日、伝達条件、報告内容、参照できる元の出来事、情報源 | 伝達処理。主人公向け表示へは選別した内容を渡す |
| `PlayerKnowledge` | 主人公が得た報告、取得日、最後に確認した事実・出典 | 掲示、会話、日誌、品の来歴、遠征一覧 |
| `NarrativeProgress` | 導入の段階、選択の記録、重要人物・品の参照 | 物語の条件判定。善悪の合計点は持たない |

`WorldEvent` は事実、`InformationReport` は誰かの主張である。誤った噂のために虚偽の世界イベントを作らない。報告は出来事の一部だけを伝えてよい。後から訂正されたときは、いつ何を聞いたかを残した上で知識を更新する。真偽の内部判定を、そのままプレイヤーへ「真実」「嘘」と表示する仕様にはしない。

UIには内部イベント全体を渡さず、知った範囲の表示モデルを渡す。犯人も凶器も未判明なら、事件の報告から内部の品UUIDを辿って正体を表示しない。NPCの価格判断や移住判断も、世界で起きたことと本人に届いた情報のどちらで動くかを区別する。

### 4.3 遠征と主人公の探索

`Expedition` は、参加者ID、出発日、目標、予定期間、物資、支援契約、現在の内部進行、最終処理日を持つ構成を提案する。既存の個人の `delve` から少数の遠征へ段階的に移す。護衛契約と、主人公が同行しない遠征への出資は別の契約にする。

遠征の実際の状態と、公表された状態は分ける。後者は出発前に知った計画と、その後に届いた報告から組み立てる。予定帰還の上限を過ぎても未確認なら「帰還遅延」。全滅を内部で知っていることだけを理由に「死亡確認」へ変えない。公的な最深到達記録と、内部で最も深く進んだ実績も分ける。

既存の `partyAndFloorNpcIds` は現在階だけでなく訪問済みの `floorStates` にいるNPCも日次処理から除外する。遠征を長期化すると、訪問済みの階に残した人物が止まり続ける可能性がある。**その場のターン処理と画面外の日次処理で、一人のNPCを同時に動かさない責任境界**を先に決める。離れた階への引き継ぎ・再訪時の復元を含め、二重死亡や品の複製を防ぐ。

### 4.4 品の所在、所有、記憶

`ItemInstance.uuid` と `itemsById` を個体の根拠として維持する。所在、所有権、貸与契約、誰が権利を主張しているかは同じ情報ではない。現行では貸与でも `owner = npc.id` になり、`NpcGearSlot.term` に約束を持つため、`owner` や `location` だけから法的な所有を判定しない。

取引、貸与、譲渡、回収、返却の入口で共通の移動・履歴処理を使う案とする。既存の `history` と `historyV2` を一度に消さず、参照と表示を移行してから整理する。

通常品の記録は要約し、物語の重要品、銘を持つ品、World Impact Items は必要な経緯を追跡する。`narrativeRole` などの意味づけをレアリティと独立させれば、幼なじみの剣を普通の安い剣のまま保持できる。素材の流通は全個体を永久保存する方式にせず、転機となる取引・流通記録に絞る案とする。

追跡することと手元から失われないことも別である。売却・返却・紛失・廃棄は成立し、その結果を記録する。紛失した重要品が通常の一品物台帳の整理で再生成されたり、遺体の保持期限により幼少期の選択まで消えたりしない設計が必要になる。

### 4.5 物語の条件と画面

幼少期の遺体調査や遺品の選択は、ゲーム側のコマンドとして記録する。`MerchantScene.ts` は入力と描画を担当し、「剣を取ったので数日後に事件が起こる」といった主要な物語条件をUIの分岐へ埋め込まない。

青い鉱石の転機も「何日目になったら強い冒険者を出す」だけにしない。売買、外への流通、価値の認識、噂、来訪の原因をたどれる構成を提案する。一方、既存の蒐集家の来訪や人物関係は、有用な個別の体験として残す。

## 5. 実装前に守る保存と移行の条件

- 執筆時点の `GameState.version` は14で、この資料整備では上げなかった。**2026-09-12 に S-3 / S-2 の実装で16へ上げている**（貸与の廃止と `merchantOrigin` の追加。移行は `save.ts` の `migrateToSingleEntrustment`）。
- [save.ts](../src/game/save.ts) の `stripRetiredFields` は `story` / `quests` などを削除する。新しい物語記録には `narrativeProgress` など別名を用いる案とし、旧キーの削除処理を無条件に外さない。
- 新規ゲームにプロローグを設けても、既存セーブに「剣を取った」「家族へ返した」などの未実施の選択を捏造しない。既存継続用の導入済み・選択未記録の扱いを設計する。
- セーブ読み込みで初期NPCの補充が行われるため、プロローグや冒険者到来前の段階へロードしただけで完成済みの町を作らないよう、初期化と移行の条件を見直す。
- 日次処理済み印、未配信報告、伝達途中の状態、受け取った知識、重要品・故人への参照を一緒に保存する。発生済みの結果はロードで再発火させない。
- `pruneCampaignRecords` / `pruneCorpses` の保持対象に、未解決の遠征、未配信報告、重要な選択からの参照を加える必要がある。遺体が消えても報告や故人の記憶まで同時に消さない。
- 現在 [merchantEconomy.test.ts](../src/game/merchantEconomy.test.ts) に10回探索後のシリアライズ文字列が60,000文字未満であるチェックがある。全イベントを無制限に蓄積しない。通常の古い出来事は要約し、重要な因果・未配信情報・選択は保持する方式を先に決める。
- 幼少期から本編までの年数経過は通常の遠征の数日経過とは別に設計する。年齢・年数が決まる前に、大量の日次処理を走らせる実装や過去の日付を固定しない。

## 6. 段階的な改善順

順序は提案であり、前の段の到達条件を満たしてから次を具体化する。大きな町シミュレーションや物語をまとめて作らず、小さな売買と一回の遠征で因果を確かめる。

| 段階 | 追加・改善する範囲 | 確認できる到達条件 |
|---|---|---|
| 0: 設計の基準 | 原文保存、物語の統合、実装差分、旧判断の再整理 | 基準・候補・現状が区別され、次の作業の参照先がある。今回の対象 |
| 1: 情報の土台 | 日次更新の窓口、事実と配信の分離、永続的な報告・知識、ギルド表示、セーブ移行 | 町で出来事が起きても地下の主人公へ自動で漏れず、帰還・報告・発見で知る。到着などの世界変化は待たない |
| 2: 遠征の一往復 | 出発、予定日、物資、数日の進行、撤退、帰還、未帰還、装備支援 | 同じ冒険者を支え、待ち、報告で結果を知る。成功・遅延・発見まで未確認の死を区別できる |
| 3: 所有と導入 | 重要品の保持、遺体での任意取得、幼少期から小さな商い、外への販売と最初の来訪 | 剣を取らなくても進行し、取った個体を売却・保管等した経緯が残る。商品が町を変える導入を遊べる |
| 4: 売却後の結果 | 少数の通常効果と個別イベント連鎖、NPCによる使用・転売、調査経路 | 人を助ける例と問題を起こす例を、売った品・相手・状況・後日の情報に結べる |
| 5: 町と攻略 | 発展、冒険者を呼ぶ理由、経済依存、多角化、攻略後 | 発展の利益と負担、迷宮終了後の暮らしの違いが、積み重ねた選択に対応する |
| 後続: ペット | 日常での関係、同行、救助操作、探索失敗との統合 | 繰り返し助け合う体験があり、固定の死で愛着を回収しない |

次は段階2の**遠征設計を先に詰め、その最小要件から段階1の型と更新順序を決める**。設計の順序と、コードの導入順序を区別する。

## 7. 次の設計単位: 冒険者の遠征

| 決める事項 | 具体化する内容 |
|---|---|
| 出発の理由 | 本人の目的・予算・危険の見積もり・商人からの支援でどう変わるか |
| パーティ | 結成・解散・人数、既存の一人の護衛とどう併存するか |
| 計画 | 目標階、見込む日数、帰還予定、商人へ伝える範囲 |
| 補給と購入 | 食料・薬・装備、所持金、購入品の使用、商人の品を選ぶ理由 |
| 日次の判断 | 前進、探索継続、野営、撤退、負傷、死亡、戦利品 |
| 商人の支援 | 販売・貸与・譲渡・出資の違い、目標への影響と本人の判断の余地 |
| 帰還・未帰還 | 帰還報告、予定超過、最後の目撃、証拠、救助依頼の条件 |
| 情報と時間 | いつ誰が何を知り、迷宮にいる商人へどの経路で伝わるか |
| 保持と再現 | セーブ中断、訪問済みの階、日次と現場の引き継ぎ、履歴の要約 |

初回は少人数・一回の支援で検証できる範囲に絞る案とする。日数や成功確率、出資の金額、物資量はここでは固定しない。

## 8. 将来の実装で確かめる場面

以下は今後の実装の受け入れ例であり、今回実装・実行済みのテストではない。日付・階数は説明用。

1. **不在中の更新**: 第30日に商人が潜り、第31〜33日も滞在する。町の到着、期限、遠征は各日一度だけ進む。地下にいるだけでは町の報告が既読にならず、帰還時に届く。
2. **到達と公表**: 第32日に冒険者が深い階へ到達し、第36日に帰還する。第35日までの掲示はその実績を表示しない。帰還報告では発生日と報告日を区別する。
3. **全滅と未帰還**: 全滅済みでも、予定日内は遠征中、超過後は帰還遅延。遺体等の発見・伝達後に初めて分かった範囲を表示し、内部の死亡階を先に漏らさない。
4. **事件と品の特定**: 犯罪の発生、町での周知、主人公の帰還、自分の売った品との同定が別々の日に成立する。早い段階の報告から品の正体を逆引きできない。
5. **目撃と噂**: 直接見た出来事はその場で知る。一部だけの証言や誤った噂を受けても世界の事実は変わらず、後の訂正が履歴として残る。
6. **剣を取らない選択**: 遺品を一切取らずにプロローグを終えられる。売却・保管・返却・紛失した場合は同じ個体の経緯が残り、魔法の武器に変質しない。
7. **支援の手応え**: 貸した・売った装備が実際に使われたときに探索へ影響する。持っているだけの品を装備扱いせず、成功だけでなく撤退等にも状況に沿った報告がある。
8. **中断と保持**: 日付変更、報告到達、品の譲渡の前後でロードしても二重更新・二重売上・複製がない。未配信の報告や重要品・故人の参照が整理処理で消えない。

実装時は上記に対応するゲームロジック・移行テストを加え、既存の `npm test` と `npm run build` を通す。物語の台詞・選択画面・掲示については、実際の操作で情報の見え方も確認する。
